# Customer Portal — ABAP Specification

**For the SAP developer. ECC 6.x, on-premise.**

You are building **41 RFC-enabled function modules** in a custom function group.
Nothing else. No HTTP, no JSON, no web server, no Gateway, no OData.

Everything here is standard ABAP: SE11 structures, SE37 function modules,
BAPIs you already use, and `BAPIRET2` for errors. You can test every single
function module by pressing F8 in SE37.

A separate service outside SAP calls these modules over RFC and does the web
work. That service is not your concern and is being built by the portal team.

---

## 1. Scope

|                |                                                                                   |
| -------------- | --------------------------------------------------------------------------------- |
| Function group | `ZCC_PORTAL` (create in SE80)                                                     |
| Naming         | `Z_CC_<AREA>_<ACTION>`                                                            |
| Package        | `ZCC` (or your local Z package)                                                   |
| All modules    | **Remote-Enabled Module** — set this on the Attributes tab, it is not the default |
| Count          | 41                                                                                |

Create the DDIC structures in §3 first. Every function module uses them.

## 2. Conventions — read once, applies to all 41

### 2.1 Every module has these parameters

**Every read module** exports:

```abap
EXPORTING
  EV_SYNCED_AT  TYPE TIMESTAMP    " set to the moment you read SAP
  ES_RETURN     TYPE BAPIRET2     " TYPE = 'S' on success
```

**Every write module** exports:

```abap
IMPORTING
  IV_REFERENCE  TYPE CHAR64       " idempotency key — see §2.4
EXPORTING
  ES_RETURN     TYPE BAPIRET2
```

Set `EV_SYNCED_AT` with:

```abap
GET TIME STAMP FIELD ev_synced_at.
```

### 2.2 Errors — use BAPIRET2, the way you always do

Do **not** raise classic exceptions and do **not** short-dump. Fill `ES_RETURN`
and return normally:

```abap
" success
es_return-type = 'S'.

" not found
es_return-type   = 'E'.
es_return-id     = 'ZCC'.
es_return-number = '001'.
es_return-message = |Customer { iv_kunnr } not found|.
```

Suggested message numbers in message class `ZCC`:

| number | meaning                   | the caller turns this into |
| ------ | ------------------------- | -------------------------- |
| 001    | record not found          | "not found"                |
| 002    | validation / bad input    | "validation"               |
| 003    | no authorisation          | "authorization"            |
| 004    | SAP subsystem unavailable | "unavailable, retry"       |

When a BAPI you call returns its own `BAPIRET2`, pass the **first `E` or `A`
message straight through**. Do not reword it. The caller logs the original and
shows the customer something friendlier.

### 2.3 Return raw SAP codes, not translated ones

Send `VBUK-GBSTK`, `VBUK-CMGST`, `VBUK-WBSTK` as the single characters SAP
stores. Do **not** convert them to words like "Open" or "Blocked". The caller
does that translation and already has the mapping table.

Same for everything else: SAP field names, SAP data types, SAP values. If a
field is `CHAR10` in SAP, make it `CHAR10` in your structure.

### 2.4 Writes must be idempotent — this one is genuinely new

The caller may send the **same write twice** — a network timeout it retried, or
a user who double-clicked. The second call must **not** post a second document.

Create this table in SE11:

```
Table ZCC_IDEMPOTENCY  (delivery class A, maintenance not allowed)

  MANDT      MANDT     CLNT 3    key
  REFERENCE  CHAR64          key   " the IV_REFERENCE passed in
  DOCUMENT   CHAR10                " the document number you created
  ERDAT      DATS
  ERZET      TIMS
  ERNAM      SYUNAME
```

Every write module follows this pattern:

```abap
" 1. already done? return the original result, post nothing
SELECT SINGLE document FROM zcc_idempotency
  INTO ev_document
  WHERE reference = iv_reference.
IF sy-subrc = 0.
  es_return-type = 'S'.
  RETURN.
ENDIF.

" 2. do the real work (BAPI + BAPI_TRANSACTION_COMMIT)
" ...

" 3. record it in the SAME logical unit of work
INSERT zcc_idempotency FROM ls_idem.
```

`IV_REFERENCE` is generated by the caller and is always the same string for the
same business action. You never generate it.

This matters most on `Z_CC_PAY_INCOMING`. It is driven by a payment gateway that
retries automatically, and a duplicate posting there is real money applied twice
to a real customer's account.

### 2.5 Lists return two flat tables, not nested ones

RFC has no nested tables. For documents with line items, export a header table
and a line table, linked by `VBELN`:

```abap
TABLES
  ET_HEADERS  STRUCTURE zcc_s_order_hdr
  ET_LINES    STRUCTURE zcc_s_doc_line   " each row carries VBELN
```

The caller reassembles them.

### 2.6 Two kinds of read — never merge them

Some areas have a customer-specific read _and_ a whole-company read:

| one customer         | whole company       |
| -------------------- | ------------------- |
| `Z_CC_INQ_LIST`      | `Z_CC_INQ_QUEUE`    |
| `Z_CC_ORD_LIST`      | `Z_CC_ORD_BLOCKED`  |
| `Z_CC_INV_LIST`      | `Z_CC_INV_REGISTER` |
| `Z_CC_AR_OPEN_ITEMS` | `Z_CC_AR_LEDGER`    |
| `Z_CC_REB_LIST`      | `Z_CC_REB_REGISTER` |

Keep these as **separate function modules**. Do not build one module with an
optional `IV_KUNNR` that returns everything when left blank.

The reason is security, not style. The customer-facing module is what a logged-in
customer's request reaches. If it could return every customer's data when one
parameter is empty, then one bug — a blank variable, a forgotten assignment —
shows customer A the orders of customer B. Two modules make that impossible.

The whole-company modules always return `KUNNR` **on every row**.

### 2.7 Never calculate GST

CGST, SGST and IGST come from `KONV` exactly as SAP calculated them. Read
condition types `JOCG`, `JOSG`, `JOIG` and pass the values through untouched.

Intra-state fills CGST + SGST and leaves IGST zero. Inter-state fills IGST and
leaves the other two zero. The caller reads _which_ fields you filled to work out
which case it was, so leave them at zero rather than filling all three.

### 2.8 Never change a credit limit

No module in this specification writes `KNKK-KLIMK`, and none should be added.
Credit masters are maintained in FD32. The portal records that a manager approved
an increase; a human still makes the change in SAP.

## 4. The 41 function modules

Signatures below omit `EV_SYNCED_AT` and `ES_RETURN` on reads, and
`IV_REFERENCE` and `ES_RETURN` on writes — §2.1 says every module has them.

### Connection (1)

**`Z_CC_PING`** — is SAP alive?
Exports `EV_OK TYPE CHAR1`. Do nothing expensive; returning `'X'` is enough. It
is called every few seconds by a health check.

### Customer master (8)

| module              | does                               | key SAP call                             |
| ------------------- | ---------------------------------- | ---------------------------------------- |
| `Z_CC_CUST_CREATE`  | create a customer master           | `BAPI_CUSTOMER_CREATEFROMDATA1` + commit |
| `Z_CC_CUST_UPDATE`  | change name / address / phone only | `BAPI_CUSTOMER_CHANGEFROMDATA1`          |
| `Z_CC_CUST_GET`     | read one customer                  | KNA1 / KNVV / ADR6                       |
| `Z_CC_CUST_SHIPTO`  | ship-to addresses                  | VBPA partner function `SH`               |
| `Z_CC_CUST_CREDIT`  | credit limit and exposure          | KNKK                                     |
| `Z_CC_REB_LIST`     | one customer's rebate agreements   | KONA                                     |
| `Z_CC_REB_REGISTER` | **all** rebate agreements          | KONA                                     |
| `Z_CC_REB_SETTLE`   | settle an agreement                | VB(7                                     |

Z_CC_CUST_GET
  IMPORTING IV_KUNNR    TYPE kunnr

Z_CC_CUST_SHIPTO
  IMPORTING IV_KUNNR    TYPE kunnr

Z_CC_CUST_CREDIT
  IMPORTING IV_KUNNR    TYPE kunnr

            ET_LINES   STRUCTURE zcc_s_doc_line

Z_CC_ORD_RELEASE_CREDIT                " VKM3
  IMPORTING IV_VBELN        TYPE vbeln
            IV_INITIATED_BY TYPE char40
  EXPORTING EV_RELEASED     TYPE char1
            EV_CMGST        TYPE char1
            EV_REASON       TYPE char60
```

Three rules here that are easy to get wrong:

**`Z_CC_ORD_SIMULATE` must create nothing.** It runs while the customer is still
looking at the checkout screen, so it may be called ten times for one eventual
order. Use SIMULATE mode and never commit.

**A credit block in `Z_CC_ORD_CREATE` is a success, not an error.** SAP creates
the order and holds it. So return the `VBELN` with `EV_CMGST = 'B'` and
`ES_RETURN-TYPE = 'S'`. Do not return an error — the portal shows the customer a
held order, which is the truth.

**`Z_CC_ORD_RELEASE_CREDIT` re-runs the credit check; it does not force the
status.** If the order is still over an unchanged limit, return
`EV_RELEASED = ' '` with SAP's reason. Reporting success anyway would leave a
warehouse expecting a pick that SAP is still blocking. A refused release is a
normal result, so `ES_RETURN-TYPE` stays `'S'`.

**`Z_CC_ORD_CANCEL`** only works on an order still fully open. Once a delivery
exists, return an `E` message — at that point the customer has to ask, not
cancel.

**`KUNAG` must be filled on every delivery header.** It is how the portal checks
that the customer asking for a delivery is allowed to see it. Reading it from
the sales order instead would mean a second lookup that can fail when SAP is
busy — and a security check that fails is a security check that lets people
through.

For `WBSTK = 'A'`, also fill `PICKED` / `PACKED` / `GOODS_ISSUED` if you have
those confirmations, so the portal can show the customer a precise stage. If you
only have `WBSTK`, leave them blank. **Do not guess** — showing "Packed" when
nothing was packed is worse than showing nothing.

Set `EV_DISCREPANCY = 'X'` when SAP recorded a quantity difference on any line.

Z_CC_AR_OPEN_ITEMS                      " BAPI_AR_ACC_GETOPENITEMS

  TABLES    ET_ITEMS STRUCTURE zcc_s_open_item

Z_CC_AR_LEDGER                          " no IV_KUNNR — §2.6, KUNNR on every row
  TABLES    ET_ITEMS STRUCTURE zcc_s_open_item

Z_CC_PAY_INCOMING                       " F-28 equivalent, post and clear
  IMPORTING IV_KUNNR   TYPE kunnr
            IV_AMOUNT  TYPE dmbtr
            IV_WAERS   TYPE waers
  TABLES    IT_ALLOCATIONS STRUCTURE zcc_s_allocation  " BELNR + amount
            ET_CLEARED     STRUCTURE zcc_s_docnum
            ET_RESIDUAL    STRUCTURE zcc_s_docnum
  EXPORTING EV_BELNR   TYPE belnr_d

Z_CC_PAY_OUTGOING                       " F-58 / F-53, pay a credit note out
  IMPORTING IV_KUNNR   TYPE kunnr
            IV_BELNR   TYPE belnr_d     " the credit note being settled
            IV_AMOUNT  TYPE dmbtr
            IV_WAERS   TYPE waers
            IV_INITIATED_BY TYPE char40
  TABLES    ET_CLEARED STRUCTURE zcc_s_docnum
  EXPORTING EV_BELNR   TYPE belnr_d
            EV_BUDAT   TYPE budat
```

`Z_CC_PAY_INCOMING` and `Z_CC_PAY_OUTGOING` are **two separate modules on
purpose**, not one module with a positive or negative amount. Money arriving and
money leaving are different postings with different authorisations. One module
that could do either depending on a sign is one typo away from paying out a
receipt.

Both must honour §2.4 idempotency. `IV_INITIATED_BY` goes onto the FI document
header text (`BKPF-BKTXT`) — otherwise SAP records the portal's technical RFC
user as the creator and the only fact worth auditing is lost.

## 5. Testing

You can test all 41 without any web tooling.

**SE37, F8.** Fill the import parameters, execute, inspect the export parameters
and tables. That is the whole loop.

**Build a test report.** A simple `ZCC_TEST` executable that calls each module
in turn and writes the results makes regression testing after a transport a
two-minute job.

**Test idempotency explicitly.** For every write module: call it once, note the
document number, call it again with the **same** `IV_REFERENCE`, and confirm you
get the same document number back and that no second document was created in the
relevant table. This is the most likely thing to be wrong and the least likely to
be noticed.

**Test the empty cases.** A customer with no orders should return an empty table
with `ES_RETURN-TYPE = 'S'`, not an error. "Nothing found" is a valid answer.

**Test authorisation.** The RFC user needs authorisation objects for every BAPI
you call. Getting this wrong shows up as a confusing failure much later, so check
it early with SU53.

## 6. What to hand over

1. A transport containing the function group, the DDIC structures, the
   `ZCC_IDEMPOTENCY` table and the `ZCC` message class.
2. RFC connection details for the portal team: **application server host, system
   number, client, system ID**.
3. A service user for the RFC connection, of type `Communications Data` (not
   `Dialog`), with the authorisations the modules need.
4. Confirmation of which **sales organisation** and **distribution channel** the
   portal should transact under.

The portal team then configures the connection and calls your modules. Nothing
about their side requires anything further from you.

## 7. Build order

Do not build all 41 at once. This order makes one area of the portal work at a
time, so problems surface while they are still small.

| #   | modules                                                             | unlocks                                                                                     |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 0   | `Z_CC_PING`, `Z_CC_CUST_GET`                                        | **proves the connection.** Build only these two, then stop and let the portal team connect. |
| 1   | the 4 catalogue modules                                             | product browsing with real prices and stock                                                 |
| 2   | the 5 order modules (`SIMULATE`, `CREATE`, `GET`, `LIST`, `CANCEL`) | customers can place real orders                                                             |
| 3   | the 4 billing + 4 AR modules                                        | real invoices and real outstanding balances                                                 |
| 4   | the 4 delivery modules                                              | shipment tracking and proof of delivery                                                     |
| 5   | the 9 pre-sales modules                                             | the sales desk, quotations                                                                  |
| 6   | remaining customer master, rebates, credit release                  | credit gauges, AP and AR desks                                                              |

Milestone 0 matters more than it looks. Almost every integration problem — wrong
host, blocked port, missing authorisation, wrong client — appears on the first
successful call. Finding it with two modules on the table is far easier than
finding it with forty-one.
