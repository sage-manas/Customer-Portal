Tracked as a checklist rather than built as application code, per docs/07's
own framing for B6 — the `gh` CLI wasn't available in the session that did
this pass, so items below are recorded here instead of as GitHub issues;
whoever has repo access should file the "Open" rows as real issues rather

| Dependency audit                      | **Done, findings triaged** | `pnpm audit` found 22 advisories (1 low, 8 moderate, 11 high, 2 critical). **All but one are dev/build-tooling only** — `eslint-plugin-boundaries`'s `handlebars`, Storybook's `uuid`, `vite`/`vitest`/`esbuild` (test runner), PostCSS/`brace-expansion` (Tailwind build) — none reach a production request. `pnpm audit --fix` was actually tried (not just read) and reverted: it forces `@opentelemetry/core` from 1.30 to 2.8+, which broke `@sentry/node` outright (`SyntaxError: ... does not provide an export named 'VERSION'`) — the exact bundling fragility ADR-043 already documented for this dependency graph. **Open:** a coordinated major-version bump across `@opentelemetry/*` + `@sentry/node` together (verified compatible first), and a separate, lower-risk bump of `eslint-plugin-boundaries` (currently pinned `^5.0.1`, latest `7.x`) with ADR-024's negative control re-run afterward to confirm boundary enforcement still works post-upgrade.                                                                                                                                                                                                                                                                                                      |

## Disaster recovery

| Item                             | Status                             | Evidence / notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backup/restore drill, documented | **Plan written, not yet executed** | `docs/runbooks/dr-backup-restore.md`. The sharpest finding from writing it, not just restating the obvious "back up Postgres": the tenant credential vault (`TenantCredential`/`TenantDataKey`, ADR-042) is encrypted under a master key that is **never stored in Postgres** — a DR drill that restores the database without separately restoring/confirming access to the master key permanently loses every tenant's stored SAP/GSTN/gateway credentials, with no technical recovery path. The runbook makes this an explicit, separately-verified drill step rather than an assumption. **Open:** actually run the drill (steps are written; execution needs a disposable environment and is genuinely operational work, not something to fake here) and record the real RTO/RPO the checklist currently has no number for. |

## Runbooks per failure mode

| Item                 | Status   | Evidence / notes                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SAP down             | **Done** | `docs/runbooks/sap-down.md` — what breaks (every SAP-owned read errors immediately, by design — ADR-016 means there's no stale cache to mask it except `@cc/adapter-cache`'s report entries, which are fail-open and self-expiring), how to tell a real outage from a mock-driver bug, and that the only automatic-retry consequence worth watching is `/admin/exceptions`'s `payment_posting_overdue` rows. |
| Payment gateway down | **Done** | `docs/runbooks/payment-gateway-down.md` — splits the failure into "gateway unreachable at checkout" (nothing stored yet, nothing to reconcile) vs "captured but webhook never arrived" (`payment_capture_unconfirmed`, recovered by `reconcilePayment` polling the gateway directly rather than re-waiting for a webhook), and an explicit "never do this" against hand-editing `Payment.state`.             |
| Queue/outbox backlog | **Done** | `docs/runbooks/queue-backlog.md` — how to tell "relay is behind" from "a BullMQ consumer is stuck," what does and doesn't degrade while it's backed up (nothing on the request path waits on the queue; only notifications/auto-tickets are delayed, never lost, per ADR-023's idempotency requirement), and the requeue mechanics `@cc/service-reconciliation` already provides.                            |

## Reading order for a new on-call engineer

1. `CLAUDE.md` rules 1–6, then this document.
2. `docs/runbooks/sap-down.md`, `payment-gateway-down.md`, `queue-backlog.md` — read once, not just when paged.
3. `docs/runbooks/dr-backup-restore.md` before the first drill, not during an actual incident.
4. `docs/DECISIONS.md` ADR-044 (reconciliation) and ADR-043 (observability) — most of the "why does this dashboard say that" questions during an incident trace back to one of these two.
